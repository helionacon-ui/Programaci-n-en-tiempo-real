C++ moderno: de los objetos a la concurrencia · Tema 6

Sincronización: mutex, variables de condición y monitores

C++ moderno: de los objetos a la concurrenciaConcurrencia

Desde cero

Objetivo: proteger los datos compartidos, hacer que un hilo espere a otro y diseñar clases seguras entre hilos (monitores).

  • La exclusión mutua es la solución a la condición de carrera: garantizar que, mientras un hilo está en la sección crítica, ningún otro entra. El mecanismo básico es el mutex (mutual exclusion), con dos operaciones: lock y unlock.
  • En C++ moderno no se llama a lock y unlock a mano: se usa lock_guard, que bloquea en su constructor y desbloquea en su destructor (RAII). Así el mutex se libera aunque se salga de la función por un return o por una excepción.
  • unique_lock es un lock_guard más flexible: se puede desbloquear y volver a bloquear, y es el que exigen las variables de condición.
  • Un mutex resuelve «no entréis a la vez», pero no «espera a que haya datos». Para eso está la variable de condición (condition_variable): un hilo hace wait y queda dormido sin consumir CPU hasta que otro hilo hace notify_one o notify_all.
  • El wait siempre se escribe con predicado: cv.wait(lk, [&]{ return hay_datos; });. El motivo es que existen los despertares espurios: un hilo puede despertar sin que nadie lo haya notificado, y el predicado lo devuelve a dormir. La forma con bucle while (!cond) cv.wait(lk); es equivalente.
  • Al hacer wait, la variable de condición libera el mutex mientras duerme y lo vuelve a tomar al despertar. Si no fuese así, nadie podría cambiar la condición y el sistema se quedaría parado.
  • Un monitor es un objeto que encapsula los datos compartidos junto con el mutex y las variables de condición que los protegen, de modo que quien lo usa no tiene que acordarse de bloquear nada. Es la forma correcta de diseñar: el main no debería ver nunca un mutex suelto.
  • El productor-consumidor con buffer limitado es el problema canónico, y cae en examen con mil disfraces (ladrones y claves, servidor y futuros, carrera de caballos). Siempre son: un mutex, una o dos variables de condición y un predicado por cada espera.
  • Un interbloqueo (deadlock) es que dos hilos se esperen mutuamente para siempre. Se evita tomando siempre los mutex en el mismo orden, o con std::lock(m1, m2), que los toma a la vez sin riesgo.
  • atomic ofrece operaciones indivisibles sobre tipos simples sin usar mutex: atomic<int>, atomic_char. Es mucho más rápido que un mutex, pero sólo sirve para operaciones de una sola variable.

Explicación ampliada

Exclusión mutua con mutex

Una sección crítica es un trozo de código que solo un hilo puede ejecutar a la vez (porque toca datos compartidos). Se protege con un mutex (de «exclusión mutua»): el hilo que lo tiene bloqueado ejecuta y los demás esperan a que lo suelte. Lo más seguro es lock_guard<mutex> lk(m);: bloquea al crearse y desbloquea solo al salir del ámbito, incluso si hay una excepción. El peligro opuesto es el interbloqueo (deadlock): el hilo A tiene el mutex 1 y pide el 2, y el B tiene el 2 y pide el 1: ninguno avanza. Se evita pidiendo siempre los mutex en el mismo orden o con scoped_lock(m1, m2).

Productor–consumidor con variable de condición

Un hilo produce datos y otro los consume, intercambiándolos por un buffer de tamaño máximo \(N\). Si el buffer está lleno, el productor debe esperar; si está vacío, el consumidor. Esperar mirando todo el rato malgasta la CPU; en su lugar se usa una variable de condición (cv.wait(lk, condicion)): el hilo se duerme hasta que otro llame a cv.notify_all(), y al despertar vuelve a comprobar la condición. Hay que usar unique_lock (no lock_guard) porque wait necesita desbloquear el mutex mientras duerme y volver a bloquearlo al despertar. Se notifica después de modificar el buffer.

Desarrollo teórico a fondo

1Exclusión mutua

Idea clave. un mutex asegura que solo un hilo a la vez ejecuta una sección crítica. Se bloquea antes de acceder a los datos compartidos y se libera al terminar.
  • std::mutex m; y std::lock_guard<std::mutex> g(m); bloquea hasta que sale del ámbito.
  • Bloquear siempre en el mismo orden evita el interbloqueo (deadlock).
Cuidado. Un mutex que se bloquea dos veces desde el mismo hilo se bloquea a sí mismo. Usa recursive_mutex solo si es necesario.
∴Variables de condición

Un hilo espera hasta que se cumpla una condición, y otro hilo lo avisa con notify_one. Así no se gasta CPU en espera activa.

Cuidado. Hay que comprobar la condición en un bucle, no una sola vez: los despertares espurios son posibles.

2Monitores

Un monitor es una clase que encapsula los datos y sus mutex. Los métodos públicos bloquean automáticamente, de forma que el acceso concurrente queda controlado.

Fórmulas y conceptos que hay que saber

  • Exclusión mutua:
#include <mutex> mutex m; int compartido = 0; void f() { lock_guard<mutex> lk(m); // bloquea aquí ++compartido; // sección crítica } // desbloquea al salir del ámbito
  • Variable de condición (el patrón completo):
#include <condition_variable> mutex m; condition_variable cv; queue<int> buffer; const size_t MAX = 10; void productor(int n) { for (int i = 0; i < n; ++i) { unique_lock<mutex> lk(m); cv.wait(lk, []{ return buffer.size() < MAX; }); // espera si lleno buffer.push(i); lk.unlock(); // desbloquear antes cv.notify_all(); // de notificar } } void consumidor() { while (true) { unique_lock<mutex> lk(m); cv.wait(lk, []{ return !buffer.empty(); }); // espera si vacío int x = buffer.front(); buffer.pop(); lk.unlock(); cv.notify_all(); procesar(x); } }
  • Monitor (la misma idea, bien encapsulada):
class Buffer { queue<int> q_; size_t max_; mutable mutex m_; condition_variable no_lleno_, no_vacio_; public: Buffer(size_t max) : max_(max) {} void poner(int x) { unique_lock<mutex> lk(m_); no_lleno_.wait(lk, [this]{ return q_.size() < max_; }); q_.push(x); lk.unlock(); no_vacio_.notify_one(); } int sacar() { unique_lock<mutex> lk(m_); no_vacio_.wait(lk, [this]{ return !q_.empty(); }); int x = q_.front(); q_.pop(); lk.unlock(); no_lleno_.notify_one(); return x; } size_t tam() const { lock_guard<mutex> lk(m_); return q_.size(); } };
  • Atómicos: atomic<int> n{0}; ++n; n.fetch_add(1); n.load(); n.store(5);
  • Evitar interbloqueo con dos mutex: lock(m1, m2); lock_guard<mutex> a(m1, adopt_lock), b(m2, adopt_lock);
  • Condiciones de Coffman (las cuatro que deben darse a la vez para que haya interbloqueo): exclusión mutua, retención y espera, no apropiación y espera circular. Romper una basta.

Método paso a paso

  1. Encuentra los datos compartidos. Todo lo que más de un hilo toque y alguno escriba.
  2. Mételos en una clase junto con su mutex: un monitor. Los métodos públicos bloquean; nadie de fuera ve el mutex.
  3. Escribe la sección crítica lo más corta posible. Nunca hagas dentro trabajo pesado ni entrada/salida.
  4. Si hay que esperar a una condición, usa condition_variable con unique_lock y siempre con predicado.
  5. Notifica después de desbloquear: si notificas con el mutex tomado, el hilo despertado se vuelve a dormir inmediatamente al no poder tomarlo.
  6. Para terminar limpiamente, usa una bandera (bool terminar_) comprobada en el predicado, y un notify_all al activarla.
  7. Comprueba que no hay interbloqueo: si hay dos mutex, ¿se toman siempre en el mismo orden?

Trampas típicas

  • Usar lock y unlock a mano. Un return o una excepción en medio deja el mutex tomado para siempre.
  • wait sin predicado. Los despertares espurios existen y el hilo seguirá como si la condición se cumpliera.
  • Usar lock_guard con una variable de condición: wait necesita unique_lock.
  • Olvidar notificar después de cambiar la condición: los hilos que esperan no despiertan nunca.
  • Notificar con el mutex tomado: el hilo despierta, no puede coger el mutex y vuelve a dormir. Funciona, pero desperdicia un cambio de contexto por notificación.
  • Proteger la lectura pero no la escritura, o al revés. Hay que proteger todos los accesos al dato compartido.
  • Olvidar mutable en el mutex de una clase si hay métodos const que lo bloquean.
  • Tomar dos mutex en órdenes distintos en dos funciones: interbloqueo garantizado antes o después.

Problema resuelto

Enunciado

Diseña una clase Futuro que guarde un valor entero que estará disponible «en algún momento», y que bloquee a cualquier hilo que intente leerlo antes de que exista. Diseña también un Servidor que entregue futuros a los hilos cliente y vaya fijando sus valores. Escribe el main con un hilo servidor y cinco clientes.

✓Ver solución paso a paso

Es el ejercicio de concurrencia del examen de febrero de 2018, y es un monitor de manual.

#include <iostream> #include <thread> #include <mutex> #include <condition_variable> #include <vector> #include <chrono> using namespace std; class Futuro { int valor_; bool disponible_; mutable mutex m_; condition_variable cv_; public: Futuro() : valor_(0), disponible_(false) {} Futuro(int v) : valor_(v), disponible_(true) {} void set_valor(int v) { lock_guard<mutex> lk(m_); if (disponible_) return; // sólo se fija una vez valor_ = v; disponible_ = true; cv_.notify_all(); // despierta a todos los lectores } int get_valor() { unique_lock<mutex> lk(m_); cv_.wait(lk, [this]{ return disponible_; }); // bloquea si no hay valor return valor_; } };

La clave del Futuro está en las tres líneas de get_valor: el unique_lock toma el mutex, el wait con predicado libera el mutex y duerme mientras no haya valor, y al despertar vuelve a tomarlo para leerlo con seguridad.

class Servidor { vector<Futuro*> futuros_; size_t siguiente_; // próximo futuro a fijar bool terminar_; mutex m_; condition_variable cv_; public: Servidor() : siguiente_(0), terminar_(false) {} ~Servidor() { for (Futuro *f : futuros_) delete f; } Futuro& servicio() // lo llama cada cliente { lock_guard<mutex> lk(m_); futuros_.push_back(new Futuro()); cv_.notify_one(); // hay trabajo para f_hilo return *futuros_.back(); } void f_hilo() // el hilo del servidor { int v = 10; while (true) { Futuro *f = nullptr; { unique_lock<mutex> lk(m_); cv_.wait(lk, [this]{ return siguiente_ < futuros_.size() || terminar_; }); if (terminar_ && siguiente_ >= futuros_.size()) return; f = futuros_[siguiente_++]; } f->set_valor(v++); // fuera del mutex del servidor this_thread::sleep_for(chrono::milliseconds(1000)); } } void terminar() { lock_guard<mutex> lk(m_); terminar_ = true; cv_.notify_all(); } };

Dos detalles importantes. Los futuros se guardan como punteros: si fueran objetos en un vector<Futuro>, al crecer el vector se reubicarían y las referencias que ya tienen los clientes quedarían colgando. Y el set_valor se hace fuera del mutex del servidor, para no tener dos mutex tomados a la vez.

void cliente(Servidor &s, int id) { for (int i = 0; i < 5; ++i) { Futuro &f = s.servicio(); cout << "[Cliente " << id << "] valor = " << f.get_valor() << endl; } } int main() { Servidor s; thread hs(&Servidor::f_hilo, &s); vector<thread> clientes; for (int i = 0; i < 5; ++i) clientes.emplace_back(cliente, ref(s), i); for (thread &t : clientes) t.join(); s.terminar(); hs.join(); return 0; }

Cómo se comporta. Los cinco clientes piden futuros enseguida y se quedan bloqueados en get_valor, sin consumir CPU. El servidor va fijando valores 10, 11, 12… a razón de uno por segundo, y cada vez despierta al cliente que esperaba ese futuro. Al terminar todos los clientes, el main pone la bandera y el hilo del servidor sale del bucle limpiamente.

Todos los ejercicios de concurrencia del examen tienen la misma estructura: una clase monitor con sus atributos compartidos, su mutex, una variable de condición por cada espera distinta y un predicado por cada wait; más una bandera de terminación. Si identificas «¿qué espera cada hilo y a qué?», el código sale solo.

Ejercicios resueltos

Intenta cada uno antes de desplegar la solución.

Ejercicio 1 · Buffer lleno

Buffer con MAX = 10. El consumidor está parado y el productor genera 25 datos. ¿Cuántos puede insertar antes de bloquearse y cuántos faltan?

✓Ver solución paso a paso

Inserta 10 (hasta llenar) y se bloquea en cv.wait porque buffer.size() < MAX es falso; quedan 15 por producir. En cuanto el consumidor saque uno y haga notify_all, el productor se despierta y mete otro.

Ejercicio 2 · Interbloqueo

El hilo A hace lock(m1); lock(m2); y el B hace lock(m2); lock(m1);. ¿Qué puede pasar y cómo se arregla?

✓Ver solución paso a paso

Puede darse interbloqueo: A tiene m1 y espera m2; B tiene m2 y espera m1; ninguno puede continuar. Soluciones: (1) que ambos pidan siempre en el mismo orden (m1 y luego m2), o (2) usar scoped_lock lk(m1, m2);, que bloquea ambos sin riesgo de interbloqueo.

Ejercicio 3 · lock_guard o unique_lock

¿Por qué cv.wait(lk, …) exige unique_lock y no lock_guard?

✓Ver solución paso a paso

wait debe desbloquear el mutex mientras el hilo duerme (si no, nadie podría modificar el buffer) y volver a bloquearlo al despertar. lock_guard no permite desbloquear manualmente; unique_lock sí. Por la misma razón, en el productor se hace lk.unlock() antes de notificar.

Autoevaluación

Responde antes de desplegar.

1¿Por qué se usa lock_guard en vez de lock y unlock?

Porque libera el mutex en su destructor, también si se sale por return o por una excepción (RAII).

2¿Qué hace cv.wait(lk, pred)?

Libera el mutex y duerme el hilo mientras el predicado sea falso; al despertar vuelve a tomar el mutex y comprueba el predicado otra vez.

3¿Por qué hay que usar predicado en el wait?

Por los despertares espurios: un hilo puede despertar sin que nadie lo notifique, y el predicado lo devuelve a dormir.

4¿Qué es un monitor?

Un objeto que encapsula los datos compartidos junto con el mutex y las variables de condición que los protegen.

5¿Cuándo usar atomic en lugar de un mutex?

Cuando basta con hacer indivisible una operación sobre una sola variable simple. Es mucho más rápido, pero no sirve para invariantes entre varias variables.

6¿Cómo se evita un interbloqueo con dos mutex?

Tomándolos siempre en el mismo orden en todo el programa, o con std::lock(m1, m2).
