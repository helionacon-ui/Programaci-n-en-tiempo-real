Programación orientada a objetos: herencia y polimorfismo

C++ moderno: de los objetos a la concurrenciaProgramación

Desde cero

Objetivo: usar herencia, métodos virtuales y clases abstractas, y entender qué decide el compilador y qué se decide en ejecución.

  • La herencia expresa una relación «es un»: un Coche es un Vehiculo. La clase derivada hereda atributos y métodos de la base y puede añadir los suyos o redefinir los que necesite.
  • Si la relación es «tiene un» (un coche tiene un motor), lo correcto no es heredar sino componer: poner un atributo. Confundir las dos es el error de diseño más frecuente.
  • El acceso protected aparece aquí: es como private pero visible para las clases derivadas. La herencia pública (class Coche : public Vehiculo) es la que corresponde a «es un»; es la que se usa prácticamente siempre.
  • Al construir un objeto derivado se llama primero al constructor de la base y luego al de la derivada; al destruirlo, al revés. Si la base no tiene constructor por defecto, hay que llamarla explícitamente en la lista de inicialización.
  • El polimorfismo es poder tratar objetos de clases distintas a través de un puntero o una referencia a la base, y que cada uno responda a su manera. Para que funcione, el método de la base debe declararse virtual.
  • La diferencia clave: sin virtual, la llamada se resuelve en tiempo de compilación según el tipo declarado (ligadura estática); con virtual, se resuelve en tiempo de ejecución según el tipo real del objeto (ligadura dinámica), consultando la tabla de funciones virtuales (vtable) que el compilador añade a la clase.
  • Una función virtual pura (= 0) no tiene implementación y convierte la clase en abstracta: no se pueden crear objetos de ella, sólo de sus derivadas, y sirve para definir una interfaz que todas deben cumplir.
  • El destructor de una clase base polimórfica debe ser virtual. Si no, al hacer delete sobre un puntero a la base sólo se ejecuta el destructor de la base y el de la derivada no se llama: fuga de memoria silenciosa.
  • El polimorfismo sólo funciona con punteros y referencias. Si guardas un objeto derivado en una variable del tipo base, se copia únicamente la parte de la base: es el object slicing, y se pierde todo lo demás sin ningún aviso.
  • friend da acceso a los miembros privados de una clase a una función o clase concreta. Rompe el encapsulamiento a propósito y en un punto controlado; su uso normal es operator<<.

Explicación ampliada

Herencia y métodos virtuales

Una clase derivada hereda atributos y métodos de la base y añade o cambia los suyos (class Circulo : public Figura). El polimorfismo permite tratar objetos distintos por su interfaz común: un vector<Figura*> puede contener círculos y rectángulos, y al llamar f->area() se ejecuta la versión del objeto real, no la del puntero. Esto solo funciona si el método es virtual en la base. Un método virtual puro (virtual double area() const = 0;) no tiene cuerpo y hace a la clase abstracta: no se pueden crear objetos de ella, solo de las derivadas que implementen el método (con override para que el compilador lo compruebe).

El destructor virtual

Si borras un objeto derivado a través de un puntero a la base (Figura *f = new Circulo(2); delete f;), C++ decide qué destructor llamar según el tipo del puntero, salvo que el destructor sea virtual. Sin virtual se ejecuta solo ~Figura() y el ~Circulo() no, así que lo propio del círculo (por ejemplo memoria dinámica) no se libera: fuga de memoria o comportamiento indefinido. Regla: toda clase pensada para ser base de otras lleva destructor virtual. Y cuidado con las ligaduras: el constructor de la base se ejecuta primero, y el del derivado después; los destructores, al revés.

Desarrollo teórico a fondo

1Herencia

Idea clave. la herencia permite crear una clase a partir de otra, reutilizando su código. La clase derivada es un caso particular de la base.
  • Herencia pública: la derivada es un subtipo de la base.
  • Los métodos virtual permiten redefinir comportamiento en la derivada.
∴Polimorfismo

Con un puntero o referencia a la base, la llamada a un método virtual ejecuta la versión del objeto real. Así se escribe código que trabaja con objetos distintos sin conocer su tipo exacto.

Cuidado. Un destructor de una clase base con herencia debe ser virtual. Si no, al borrar por puntero base no se destruye la parte derivada.

2Coste del polimorfismo

Una llamada virtual se resuelve en tiempo de ejecución con una tabla de funciones. Tiene un pequeño coste, que en sistemas de tiempo real puede importar y ha de tenerse en cuenta.

Fórmulas y conceptos que hay que saber

  • Herencia y polimorfismo:
class Figura { // clase abstracta protected: string nombre_; public: Figura(const string &n) : nombre_(n) {} virtual ~Figura() {} // destructor VIRTUAL virtual double area() const = 0; // virtual pura virtual void describir() const // virtual con implementación { cout << nombre_ << " de área " << area() << endl; } }; class Circulo : public Figura { double r_; public: Circulo(double r) : Figura("Círculo"), r_(r) {} double area() const override { return 3.14159265 * r_ * r_; } }; class Rectangulo : public Figura { double a_, b_; public: Rectangulo(double a, double b) : Figura("Rectángulo"), a_(a), b_(b) {} double area() const override { return a_ * b_; } }; int main() { vector<Figura*> v; v.push_back(new Circulo(1.0)); v.push_back(new Rectangulo(2.0, 3.0)); for (Figura *f : v) f->describir(); // cada uno responde a su manera for (Figura *f : v) delete f; // gracias al destructor virtual }
  • override: marca que el método redefine uno virtual de la base. Si te equivocas en la firma, el compilador lo detecta. Úsalo siempre.
  • Orden de construcción: base → derivada. De destrucción: derivada → base.
  • Coste: una llamada virtual añade una indirección por la vtable; cada objeto polimórfico guarda un puntero a su tabla.
  • Clase abstracta: tiene al menos un método virtual puro; no se pueden instanciar objetos de ella.
  • dynamic_cast<Derivada*>(p) convierte de base a derivada comprobando en ejecución; devuelve nullptr si el objeto no es de ese tipo.

Método paso a paso

  1. Decide si hay herencia: pregúntate si es «es un» o «tiene un». Si es «tiene un», compón.
  2. Pon en la base lo común y declara virtual todo lo que cada derivada vaya a hacer de forma distinta.
  3. Destructor virtual en la base, siempre que vaya a usarse polimórficamente.
  4. En cada derivada, llama al constructor de la base en la lista de inicialización y marca los métodos redefinidos con override.
  5. Guarda los objetos en un vector<Base*> (o de punteros inteligentes) y recórrelos: ahí se ve el polimorfismo.
  6. Libera con delete lo que reservaste con new.

Trampas típicas

  • Olvidar virtual en el método de la base. El código compila y se ejecuta, pero siempre llama a la versión de la base: es el fallo más difícil de ver.
  • Olvidar el destructor virtual. No da ningún error visible: simplemente no se libera la parte derivada.
  • Guardar objetos derivados en un vector<Base> en vez de vector<Base*>: object slicing, se pierde la parte derivada.
  • Usar herencia para reutilizar código cuando no hay relación «es un». Produce jerarquías absurdas (una Pila no es un vector).
  • Intentar crear un objeto de una clase abstracta: no compila, y es la señal de que falta implementar algún método virtual puro.
  • Acceder a atributos private de la base desde la derivada. Hay que declararlos protected o pasar por los métodos.

Problema resuelto

Enunciado

Diseña una jerarquía de sensores para un sistema de adquisición: todos tienen identificador y devuelven una lectura, pero un sensor de temperatura y uno de presión la calculan de forma distinta y tienen unidades distintas. Escribe la clase base, dos derivadas y un main que las recorra polimórficamente. Explica qué pasaría sin virtual.

✓Ver solución paso a paso
#include <iostream> #include <vector> #include <string> using namespace std; class Sensor { // clase abstracta protected: int id_; double bruto_; // valor del conversor A/D public: Sensor(int id) : id_(id), bruto_(0.0) {} virtual ~Sensor() {} // IMPRESCINDIBLE void set_bruto(double v) { bruto_ = v; } int get_id() const { return id_; } virtual double lectura() const = 0; // cada sensor la calcula virtual string unidad() const = 0; void mostrar() const // común a todos { cout << "Sensor " << id_ << ": " << lectura() << " " << unidad() << endl; } }; class Temperatura : public Sensor { double offset_, ganancia_; public: Temperatura(int id, double off, double gan) : Sensor(id), offset_(off), ganancia_(gan) {} double lectura() const override { return bruto_ * ganancia_ + offset_; } string unidad() const override { return "ºC"; } }; class Presion : public Sensor { double escala_; public: Presion(int id, double esc) : Sensor(id), escala_(esc) {} double lectura() const override { return bruto_ * escala_; } string unidad() const override { return "bar"; } }; int main() { vector<Sensor*> sensores; sensores.push_back(new Temperatura(1, -40.0, 0.125)); sensores.push_back(new Presion(2, 0.004)); sensores[0]->set_bruto(800); sensores[1]->set_bruto(2500); for (const Sensor *s : sensores) s->mostrar(); for (Sensor *s : sensores) delete s; return 0; }

Salida:

Sensor 1: 60 ºC Sensor 2: 10 bar

Comprobación: \(800\cdot0{,}125-40=100-40=60\) ºC y \(2500\cdot0{,}004=10\) bar.

Qué pasa sin virtual. Si lectura() no fuera virtual, no podría ser pura y habría que darle una implementación en la base. Entonces mostrar(), que es un método de Sensor, llamaría siempre a Sensor::lectura() aunque el objeto real fuese un Temperatura: el compilador resolvería la llamada mirando el tipo declarado. El programa compilaría, se ejecutaría y daría resultados mal sin ningún aviso. Con virtual, la llamada pasa por la vtable del objeto real y cada sensor devuelve lo suyo.

Y sin destructor virtual. El delete s sobre un Sensor* ejecutaría sólo ~Sensor(). Aquí las derivadas no reservan memoria, así que no se notaría; en cuanto una derivada tenga un new propio, hay fuga. Por eso la regla es: destructor virtual en toda clase base polimórfica, siempre, sin pensarlo.

Lo que de verdad aporta esta jerarquía: el main y la función mostrar() no saben qué sensores existen. Añadir un sensor de caudal mañana no obliga a tocar ni una línea de código existente, sólo a escribir la clase nueva. Eso es lo que hay que decir si el examen pregunta «qué ventaja aporta el polimorfismo».

Ejercicios resueltos

Intenta cada uno antes de desplegar la solución.

Ejercicio 1 · Polimorfismo con un vector

vector<Figura*> con un Círculo de radio 2 y un Rectángulo 3×4. ¿Cuánto suma area() de todos?

✓Ver solución paso a paso

Círculo: \(\pi\cdot2^2=12{,}566\). Rectángulo: \(3\cdot4=12\). Total \(=24{,}566\). La llamada elige la versión correcta de area() en tiempo de ejecución (porque es virtual).

Ejercicio 2 · Destructor no virtual

¿Qué ocurre si Figura no tiene destructor virtual y se hace delete f; con f apuntando a un Circulo?

✓Ver solución paso a paso

Solo se ejecuta ~Figura(); el destructor de Circulo no se llama, y lo que éste liberase queda sin liberar (fuga) o, formalmente, el comportamiento es indefinido. Solución: virtual ~Figura() {}.

Ejercicio 3 · Clase abstracta

¿Compila Figura f("x"); si area() es virtual pura? ¿Y Figura *p = new Circulo(1);?

✓Ver solución paso a paso

Figura f("x"); no compila: la clase es abstracta y no se pueden crear objetos de ella. Figura *p = new Circulo(1); sí: Circulo implementa area(), y el puntero a la base puede apuntar a un objeto derivado.

Autoevaluación

Responde antes de desplegar.

1¿Cuándo hay que usar herencia y cuándo composición?

Herencia para «es un»; composición (un atributo) para «tiene un».

2¿Qué diferencia hay entre ligadura estática y dinámica?

La estática se resuelve en compilación según el tipo declarado; la dinámica, en ejecución según el tipo real, usando la vtable. La segunda requiere virtual.

3¿Por qué el destructor de una base polimórfica debe ser virtual?

Porque si no, al hacer delete sobre un puntero a la base no se ejecuta el destructor de la derivada y se produce una fuga de memoria.

4¿Qué es el object slicing?

Guardar un objeto derivado en una variable del tipo base: se copia sólo la parte de la base y se pierde el resto, sin aviso del compilador.

5¿Qué hace que una clase sea abstracta?

Tener al menos un método virtual puro (= 0). No se pueden crear objetos de ella.

6¿Para qué sirve override?

Para decirle al compilador que el método redefine uno virtual de la base; si la firma no coincide, da error en vez de crear un método nuevo por error.
