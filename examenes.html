Problema 1 · Cifrado por primeras letras con un map 2018 T2

Enunciado

Haz un programa para cifrar y descifrar mensajes formados por la primera letra de cada frase (delimitadas por punto y seguido); el espacio del mensaje secreto se convierte en salto de línea. Para cifrar existe un fichero dict.txt con una frase que empieza por cada letra del alfabeto, en cualquier orden. Usa un mapa para guardar la frase de cada letra.
✓Solución completa

El ejercicio no es de cifrado sino de map + ficheros + strings, que es lo que de verdad se evalúa.

map<char,string> cargar_diccionario(const string &fichero) { map<char,string> dic; ifstream f(fichero); if (!f) return dic; string linea; while (getline(f, linea)) if (!linea.empty()) dic[tolower(linea[0])] = linea; // la clave es la primera letra return dic; } string cifrar(const string &secreto, const map<char,string> &dic) { string salida; for (char c : secreto) { if (c == ' ') { salida += "\n"; continue; } // espacio -> salto auto it = dic.find(tolower(c)); if (it == dic.end()) continue; // sin frase para esa letra salida += it->second; if (salida.back() != '.') salida += '.'; salida += ' '; // separador tras el punto } return salida; } string descifrar(const string &fichero) { ifstream f(fichero); string texto((istreambuf_iterator<char>(f)), istreambuf_iterator<char>()); string secreto; bool inicio = true; for (size_t i = 0; i < texto.size(); ++i) { if (inicio && isalpha(static_cast<unsigned char>(texto[i]))) { secreto += texto[i]; inicio = false; } if (texto[i] == '.') inicio = true; // empieza otra frase if (texto[i] == '\n') secreto += ' '; // salto -> espacio } return secreto; }

Comprobación con el ejemplo del enunciado. «Toledo está cerca de Madrid. Integrada con el monte que la rodea. Empedradas tiene la mayoría de las calles. Más parece que no pasa el tiempo por ella. Podría decirse que está como siempre. O tal vez mejor.» → primeras letras T, I, E, M, P, O → «Tiempo» ✓

Los tres puntos que puntúan: usar find en el map y no operator[] (que crearía entradas vacías al cifrar una letra sin frase); tratar el espacio y el salto de línea como casos aparte; y llevar la bandera inicio para saber cuándo empieza frase al descifrar.

Problema 2 · Clase Futuro y servidor concurrente 2018 T6

Enunciado

Diseña una clase Futuro que guarde un entero disponible «en algún momento» y que bloquee a quien intente leerlo antes de tiempo, con set_valor (una sola vez) y get_valor. Diseña un Servidor con un método servicio que entregue futuros, un f_hilo que los vaya fijando con valores consecutivos desde 10 (durmiendo 1000 ms entre uno y otro) y un terminar limpio. Escribe el main con un hilo servidor y cinco clientes.
✓Solución completa

Es un monitor con variable de condición. La clase Futuro completa:

class Futuro { int valor_; bool disponible_; mutable mutex m_; condition_variable cv_; public: Futuro() : valor_(0), disponible_(false) {} Futuro(int v) : valor_(v), disponible_(true) {} void set_valor(int v) { lock_guard<mutex> lk(m_); if (disponible_) return; // sólo una vez valor_ = v; disponible_ = true; cv_.notify_all(); } int get_valor() { unique_lock<mutex> lk(m_); cv_.wait(lk, [this]{ return disponible_; }); return valor_; } };

Y el servidor, con su propia variable de condición para esperar a que haya un futuro nuevo que rellenar y una bandera de terminación:

class Servidor { vector<Futuro*> futuros_; size_t siguiente_ = 0; bool terminar_ = false; mutex m_; condition_variable cv_; public: ~Servidor() { for (Futuro *f : futuros_) delete f; } Futuro& servicio() { lock_guard<mutex> lk(m_); futuros_.push_back(new Futuro()); cv_.notify_one(); return *futuros_.back(); } void f_hilo() { int v = 10; while (true) { Futuro *f; { unique_lock<mutex> lk(m_); cv_.wait(lk, [this]{ return siguiente_ < futuros_.size() || terminar_; }); if (terminar_ && siguiente_ >= futuros_.size()) return; f = futuros_[siguiente_++]; } f->set_valor(v++); this_thread::sleep_for(chrono::milliseconds(1000)); } } void terminar() { lock_guard<mutex> lk(m_); terminar_ = true; cv_.notify_all(); } };

Los cuatro puntos que decide el corrector:

  1. Los futuros se guardan como punteros. Si fueran objetos en un vector<Futuro>, al crecer el vector se reubicarían y las referencias que ya tienen los clientes quedarían colgando.
  2. El wait lleva predicado, en las dos clases.
  3. set_valor se llama fuera del mutex del servidor, para no tener dos mutex tomados a la vez.
  4. La terminación es limpia: una bandera dentro del predicado y un notify_all.

Comportamiento: los cinco clientes piden sus futuros y se quedan bloqueados sin consumir CPU; el servidor los va fijando a 10, 11, 12… uno por segundo y despierta a cada cliente cuando le toca.

Problema 3 · Análisis de planificabilidad con techo de prioridad 2016 T9

Enunciado

Un sistema tiene 3 tareas y 2 objetos compartidos. \(\tau_C\): periódica, \(T=120\), \(C=12\), \(D=120\), usa O1 (2 ms) y O2 (3 ms). \(\tau_B\): esporádica, \(T=500\), \(C=8\), \(D=25\), usa O1 (3) y O2 (1). \(\tau_A\): periódica, \(T=20\), \(C=10\), \(D=20\), usa O1 (4). Con prioridades monotónicas en plazo y techo de prioridad inmediato: a) prioridades y techos; b) bloqueos; c) tiempos de respuesta. ¿Está garantizado?
✓Solución completa

a) DM ordena por plazo: \(\tau_A\) (D=20) prioridad 1, \(\tau_B\) (25) prioridad 2, \(\tau_C\) (120) prioridad 3. Techos: O1 lo usan las tres → techo = prioridad de \(\tau_A\); O2 lo usan \(\tau_B\) y \(\tau_C\) → techo = prioridad de \(\tau_B\).

b) Bloqueo = sección crítica más larga de una tarea menos prioritaria sobre un recurso con techo ≥ su prioridad:

TareaCandidatas\(B_i\)
\(\tau_A\)O1 de \(\tau_B\) (3) y de \(\tau_C\) (2)3 ms
\(\tau_B\)O1 de \(\tau_C\) (2) y O2 de \(\tau_C\) (3)3 ms
\(\tau_C\)ninguna por debajo0

c) \(U=10/20+8/500+12/120=0{,}616\).

\[R_A=10+3=13\le20\ \checkmark\] \[R_B=8+3+\left\lceil\frac{R_B}{20}\right\rceil10:\quad 11\to21\to31\to31,\qquad R_B=31>25\ \times\] \[R_C=12+\left\lceil\frac{R_C}{20}\right\rceil10+\left\lceil\frac{R_C}{500}\right\rceil8:\quad 12\to30\to40\to40,\qquad R_C=40\le120\ \checkmark\]

El sistema no está garantizado: \(\tau_B\) necesita 31 ms en el peor caso y su plazo es 25.

La utilización, 0,616, parecía cómoda. Lo que hunde a \(\tau_B\) es que \(\tau_A\) la interrumpe dos veces (porque \(R_B\) supera los 20 ms de \(T_A\)) más los 3 ms de bloqueo. Con \(C_A=7\) saldría exactamente 25 y cumpliría.

Problema 4 · Ejecutivo cíclico 2016 T8

Enunciado

Describe qué es un ejecutivo cíclico, sus ventajas e inconvenientes, y escribe el código para este conjunto de tareas: \(\tau_C\) (T=120, C=12), \(\tau_B\) (T=80, C=8), \(\tau_A\) (T=40, C=10) ms, sabiendo que su código está en f_a(), f_b() y f_c().
✓Solución completa

Qué es. Un único bucle que llama a las tareas en un orden calculado de antemano, sin sistema operativo ni hilos. El tiempo se divide en marcos de duración fija (el ciclo menor) y el esquema se repite cada hiperperiodo.

Cálculo. \(H=\operatorname{mcm}(40,80,120)=240\) ms · \(f=\operatorname{mcd}=40\) ms (divide a los tres periodos y \(40\ge\max C_i=12\) ✓) · \(240/40=6\) marcos. \(U=10/40+8/80+12/120=0{,}45\).

MarcotTareasCarga
00A, B, C30 / 40
140A10
280A, B18
3120A, C22
4160A, B18
5200A10
int main() { const auto F = chrono::milliseconds(40); int marco = 0; auto siguiente = chrono::steady_clock::now(); while (true) { if (marco % 1 == 0) f_a(); // cada 40 ms if (marco % 2 == 0) f_b(); // cada 80 ms if (marco % 3 == 0) f_c(); // cada 120 ms marco = (marco + 1) % 6; siguiente += F; this_thread::sleep_until(siguiente); } }

Usar sleep_until sobre un instante acumulado y no sleep_for(40ms) es importante: con sleep_for el periodo real sería 40 ms más lo que tarden las tareas, y el error se acumularía.

Ventajas: determinista y verificable de antemano, sin sobrecarga de sistema operativo, sin cambios de contexto y sin exclusión mutua ni interbloqueos, porque no hay concurrencia real. Inconvenientes: rígido (cualquier cambio obliga a recalcular el esquema), hay que trocear a mano las tareas más largas que el ciclo menor, encaja mal las tareas esporádicas y exige periodos armónicos para que el esquema sea manejable.

Problema 5 · Herencia y polimorfismo: jerarquía de figuras tipo T4

Enunciado

Diseña una jerarquía con una clase abstracta Figura y dos derivadas, cada una con su cálculo de área. Guárdalas en un vector y recórrelas polimórficamente. Explica qué ocurre si se olvida virtual y si se olvida el destructor virtual.
✓Solución completa
class Figura { protected: string nombre_; public: Figura(const string &n) : nombre_(n) {} virtual ~Figura() {} // destructor virtual virtual double area() const = 0; // virtual pura -> clase abstracta void describir() const { cout << nombre_ << ": " << area() << endl; } }; class Circulo : public Figura { double r_; public: Circulo(double r) : Figura("Círculo"), r_(r) {} double area() const override { return 3.14159265 * r_ * r_; } }; class Rectangulo : public Figura { double a_, b_; public: Rectangulo(double a, double b) : Figura("Rectángulo"), a_(a), b_(b) {} double area() const override { return a_ * b_; } }; int main() { vector<Figura*> v{ new Circulo(1.0), new Rectangulo(2.0, 3.0) }; for (const Figura *f : v) f->describir(); for (Figura *f : v) delete f; }

Sin virtual: describir() es un método de Figura y la llamada a area() se resolvería en compilación mirando el tipo declarado. Se ejecutaría siempre Figura::area() aunque el objeto fuese un Circulo. El programa compila, se ejecuta y da resultados equivocados sin ningún aviso.

Sin destructor virtual: el delete f sobre un Figura* ejecutaría sólo ~Figura(). Si alguna derivada reservase memoria propia, esa memoria no se liberaría nunca: fuga silenciosa.

Y si se guardasen en un vector<Figura> en vez de punteros, ni siquiera compilaría (la clase es abstracta); con una base no abstracta compilaría y se produciría object slicing: se copiaría sólo la parte de Figura.

Problema 6 · Criba de Eratóstenes en paralelo práctica T5

Enunciado

Calcula todos los primos hasta 1 000 000 con la criba de Eratóstenes, usando varios hilos y std::atomic_char para el vector de marcas. Mide los tiempos y comprueba el resultado con los ocho últimos primos del rango.
✓Solución completa
#include <array> #include <atomic> #include <thread> #include <chrono> #include <vector> #include <iostream> using namespace std; const int N = 1000000; array<atomic_char, N> criba; // 'd' desconocido, 'p' primo, 'c' compuesto void marcar(int desde, int hasta) { for (int i = desde; i <= hasta; ++i) { if (criba[i] != 'd') continue; // ya lo ha procesado otro hilo criba[i] = 'p'; for (long j = (long)i * i; j < N; j += i) criba[j] = 'c'; // no pasa nada si se repite } } int main() { for (int i = 0; i < N; ++i) criba[i] = 'd'; criba[0] = criba[1] = 'c'; auto t0 = chrono::steady_clock::now(); const int H = 4, lim = (int)sqrt(N); vector<thread> hilos; int bloque = lim / H; for (int k = 0; k < H; ++k) hilos.emplace_back(marcar, 2 + k*bloque, (k == H-1) ? lim : 1 + (k+1)*bloque); for (thread &t : hilos) t.join(); for (int i = 2; i < N; ++i) if (criba[i] == 'd') criba[i] = 'p'; auto t1 = chrono::steady_clock::now(); cout << chrono::duration_cast<chrono::milliseconds>(t1-t0).count() << " ms\n"; int n = 0; for (int i = N-1; i >= 2 && n < 8; --i) if (criba[i] == 'p') { cout << i << " "; ++n; } }

Comprobación. Los ocho últimos primos por debajo de un millón son 999907, 999917, 999931, 999953, 999959, 999961, 999979 y 999983. Si tu programa no los saca exactamente, hay un error de límites.

Por qué funciona sin mutex. Las escrituras son idempotentes: marcar dos veces un número como compuesto da el mismo resultado. Lo único que hay que garantizar es que la escritura de un carácter no se parta por la mitad, y de eso se encarga atomic_char. Si se usara un char normal, el programa casi siempre funcionaría, que es la peor situación posible.

Sobre los tiempos. Sólo hace falta cribar hasta \(\sqrt{N}=1000\): más allá, todo lo que quede en «desconocido» es primo. La aceleración está lejos del número de hilos porque el programa está limitado por el acceso a memoria, no por la CPU: un millón de posiciones no caben en la caché.

Problema 7 · Planificación FCFS, SJF y Round-Robin tipo T7

Enunciado

Cuatro procesos: P1 (llega en 0, CPU 8), P2 (1, 4), P3 (2, 9) y P4 (3, 5). Calcula los tiempos medios de espera y retorno con FCFS, SJF no expulsivo y Round-Robin con quantum 4. ¿Cuál elegirías para un sistema interactivo?
✓Solución completa

FCFS: P1 (0-8), P2 (8-12), P3 (12-21), P4 (21-26).

Retornos 8, 11, 19, 23 → media 15,25. Esperas 0, 7, 10, 18 → media 8,75.

SJF no expulsivo: en t = 8 han llegado los tres y se elige el más corto, P2; luego P4 y por último P3.

P1 (0-8), P2 (8-12), P4 (12-17), P3 (17-26). Retornos 8, 11, 24, 14 → media 14,25. Esperas 0, 7, 15, 9 → media 7,75.

Round-Robin, q = 4: P1 (0-4), P2 (4-8, termina), P3 (8-12), P4 (12-16), P1 (16-20, termina), P3 (20-24), P4 (24-25, termina), P3 (25-26, termina).

Retornos: P1 20, P2 7, P3 24, P4 22 → media 18,25. Esperas: 12, 3, 15, 17 → media 11,75.

AlgoritmoEspera mediaRetorno medioCambios de contexto
FCFS8,7515,253
SJF7,7514,253
Round-Robin11,7518,257

Para un sistema interactivo, Round-Robin, aunque sus medias sean las peores. El motivo es el tiempo de respuesta: con RR los cuatro procesos empiezan a ejecutarse en los primeros 16 ms, mientras que con SJF P3 no empieza hasta el instante 17. En un sistema interactivo el usuario nota cuándo empieza a responder su programa, no cuándo termina. Además, SJF puede dejar un proceso largo sin ejecutar indefinidamente si siguen llegando cortos, y RR no.

Problema 8 · Controlador difuso de Sugeno tipo T10

Enunciado

Diseña un controlador de Sugeno para un ventilador con tres conjuntos triangulares de temperatura: fría (10, 15, 20), templada (18, 23, 28) y caliente (26, 32, 38) ºC, con salidas 0, 50 y 100 %. Calcula la salida para 19 ºC y 27 ºC e impleméntalo en C++.
✓Solución completa

Para 19 ºC: \(\mu_{fría}=\frac{20-19}{20-15}=0{,}20\), \(\mu_{templada}=\frac{19-18}{23-18}=0{,}20\), \(\mu_{caliente}=0\).

\[z^{*}=\frac{0{,}20\cdot0+0{,}20\cdot50}{0{,}40}=\frac{10}{0{,}40}=\boxed{25\ \%}\]

Para 27 ºC: \(\mu_{templada}=\frac{28-27}{28-23}=0{,}20\), \(\mu_{caliente}=\frac{27-26}{32-26}=0{,}1667\).

\[z^{*}=\frac{0{,}20\cdot50+0{,}1667\cdot100}{0{,}3667}=\frac{26{,}67}{0{,}3667}=\boxed{72{,}7\ \%}\]
struct Triangular { double a, b, c; double grado(double x) const { if (x <= a || x >= c) return 0.0; if (x < b) return (x - a) / (b - a); if (x > b) return (c - x) / (c - b); return 1.0; } }; struct Regla { Triangular conjunto; double salida; }; double sugeno(const vector<Regla> &reglas, double x) { double num = 0.0, den = 0.0; for (const Regla &r : reglas) { double w = r.conjunto.grado(x); num += w * r.salida; den += w; } return (den > 1e-9) ? num / den : 0.0; // evitar 0/0 }

Con reglas = { {{10,15,20},0}, {{18,23,28},50}, {{26,32,38},100} } se obtiene 19 ºC → 25 %, 23 ºC → 50 %, 27 ºC → 72,7 % y 35 ºC → 100 %.

Con dos entradas (por ejemplo temperatura y humedad), cada regla llevaría dos conjuntos y el peso sería el mínimo de los dos grados: ese es el operador Y de la lógica difusa. Todo lo demás del código se queda igual.
