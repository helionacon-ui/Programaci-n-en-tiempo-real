Concurrencia: hilos en C++11

C++ moderno: de los objetos a la concurrenciaConcurrencia

Desde cero

Objetivo: lanzar hilos, pasarles parámetros y recoger resultados, y entender por qué la ejecución intercalada rompe el código secuencial.

  • Un programa concurrente es un programa con varios «main» a la vez. Cada hilo ejecuta una función y, dentro de ella, el código es secuencial; pero cada hilo avanza a su ritmo y el orden en que se intercalan sus instrucciones es impredecible.
  • La distinción que hay que tener clara: proceso = hilos + recursos. Un proceso tiene su propio espacio de memoria; los hilos de un mismo proceso comparten la memoria. Por eso comunicarse entre hilos es barato y por eso aparecen las condiciones de carrera.
  • Un hilo se crea construyendo un objeto std::thread con la función que debe ejecutar y sus argumentos. El hilo empieza a ejecutarse inmediatamente, en paralelo con el que lo creó.
  • Antes de destruir un thread hay que decidir qué hacer con él: join() espera a que termine, detach() lo desliga y lo deja corriendo por su cuenta. Si no haces ninguna de las dos, el destructor llama a terminate() y el programa aborta.
  • La función de un hilo devuelve void: los resultados salen por referencia, y para pasar una referencia a thread hay que envolverla en std::ref(x), porque por defecto los argumentos se copian.
  • Una condición de carrera ocurre cuando dos hilos acceden a la misma variable y al menos uno escribe, sin sincronización. El resultado depende del orden de ejecución, que cambia de una ejecución a otra. El ejemplo canónico es contador++: no es una operación atómica, sino leer, sumar y escribir, y entre esos tres pasos puede colarse otro hilo.
  • Los errores de concurrencia son no deterministas: un programa mal sincronizado puede funcionar cien veces seguidas y fallar la ciento uno, o fallar sólo en otra máquina. Por eso no se depuran a base de ejecutar: se razonan.
  • Un hilo también puede ejecutar un método de un objeto: thread h{&Clase::metodo, &objeto, args...}. Se pasa el puntero al método y el puntero al objeto sobre el que invocarlo.
  • El paralelismo real depende del hardware: thread::hardware_concurrency() da una idea de cuántos hilos pueden ejecutarse a la vez. Crear muchos más hilos que núcleos no acelera nada y añade cambios de contexto.

Explicación ampliada

Qué es un hilo y para qué sirve

Un hilo es una línea de ejecución dentro de un programa. Con varios hilos, el programa puede hacer cosas a la vez (en varios núcleos) o repartir el tiempo de un núcleo entre ellas. Se lanza con thread h(funcion, args…) y se espera su final con h.join() (si no se hace join, el programa se aborta). Dos detalles que fallan siempre: los argumentos se copian, así que para que un hilo modifique una variable hay que pasarla con ref(x); y un método de objeto se lanza como thread h(&Clase::metodo, &obj, args…).

Condiciones de carrera y ley de Amdahl

Cuando dos hilos modifican la misma variable sin protección hay una condición de carrera: ++n no es una operación única, sino leer, sumar y escribir, y dos hilos pueden leer el mismo valor y pisarse (se pierden incrementos). El resultado es impredecible y cambia de una ejecución a otra. Se arregla con exclusión mutua (mutex) o con tipos atomic. Y paralelizar no siempre da una mejora proporcional: si una fracción \(f\) del programa es secuencial, la ley de Amdahl dice que con \(N\) núcleos la aceleración es \(S=\dfrac{1}{f+\frac{1-f}{N}}\), con límite \(1/f\).

Fórmulas y conceptos que hay que saber

  • Lanzar hilos:
#include <thread> #include <iostream> using namespace std; void trabajo(int id, int n, int &resultado) // resultado POR REFERENCIA { int s = 0; for (int i = 1; i <= n; ++i) s += i; resultado = s; cout << "Hilo " << id << " termina\n"; } int main() { int r1 = 0, r2 = 0; thread h1(trabajo, 1, 100, ref(r1)); // ref() es obligatorio thread h2(trabajo, 2, 200, ref(r2)); h1.join(); // esperar a que acaben h2.join(); cout << r1 << " " << r2 << endl; // 5050 20100 }
  • Hilo que ejecuta un método:
class Contador { int n_ = 0; public: void sumar(int veces) { for (int i=0;i<veces;++i) ++n_; } int get() const { return n_; } }; Contador c; thread h{&Contador::sumar, &c, 1000}; h.join();
  • Vector de hilos (el patrón habitual):
vector<thread> hilos; for (int i = 0; i < N; ++i) hilos.emplace_back(trabajo, i, 100, ref(res[i])); for (thread &h : hilos) h.join();
  • Dormir y medir tiempos:
#include <chrono> this_thread::sleep_for(chrono::milliseconds(100)); auto t0 = chrono::steady_clock::now(); // ... trabajo ... auto t1 = chrono::steady_clock::now(); cout << chrono::duration_cast<chrono::microseconds>(t1-t0).count() << " us\n";
  • Aceleración (speed-up): \(S=\dfrac{T_1}{T_p}\) con \(p\) hilos. Ley de Amdahl: si una fracción \(f\) del programa es secuencial, \(S\le\dfrac{1}{f+\frac{1-f}{p}}\le\dfrac1f\).

Método paso a paso

  1. Identifica el trabajo que puede hacerse en paralelo y escríbelo como una función que no dependa del orden: idealmente, cada hilo trabaja sobre una parte distinta de los datos.
  2. Escribe la función del hilo con los parámetros que necesita y los resultados por referencia.
  3. Lanza los hilos, normalmente en un vector<thread> con emplace_back.
  4. Haz join() de todos antes de leer los resultados. Hasta ese momento, los resultados no son fiables.
  5. Busca los datos compartidos: toda variable que más de un hilo toque y alguno escriba necesita protección (tema 6).
  6. Mide con chrono y compara con la versión de un solo hilo. Si no mejora, pregúntate cuánto hay de verdad paralelizable.

Trampas típicas

  • Olvidar join() o detach(): el programa aborta al destruir el objeto thread.
  • Pasar una referencia sin ref(): el hilo recibe una copia y el resultado nunca llega al original. Si la función espera int&, ni siquiera compila; si espera un objeto, compila y falla en silencio.
  • Leer el resultado antes del join().
  • Pasar a un hilo una referencia o un puntero a una variable local de una función que puede terminar antes: el hilo se queda apuntando a memoria muerta.
  • Suponer un orden de ejecución entre hilos. Si el enunciado exige un orden, hay que imponerlo con sincronización.
  • Escribir en cout desde varios hilos sin proteger: la salida sale entremezclada. No corrompe nada, pero es ilegible.
  • Crear un hilo por elemento de un vector de un millón de elementos. El coste de crear hilos y de los cambios de contexto se come la ganancia.

Problema resuelto

Enunciado

Haz un programa que sume dos matrices de 1000×1000 con 1, 2 y 4 hilos, midiendo el tiempo de cada versión. Después, un contador compartido incrementado por 4 hilos 100 000 veces cada uno: ¿cuánto vale al final y por qué?

✓Ver solución paso a paso

1) Suma de matrices en paralelo. Cada hilo se ocupa de un bloque de filas, así que no hay datos compartidos en escritura y no hace falta ninguna protección: es el caso ideal.

#include <iostream> #include <thread> #include <vector> #include <chrono> using namespace std; const int N = 1000; static double a[N][N], b[N][N], c[N][N]; void sumar_filas(int desde, int hasta) { for (int i = desde; i < hasta; ++i) for (int j = 0; j < N; ++j) c[i][j] = a[i][j] + b[i][j]; } double medir(int nhilos) { auto t0 = chrono::steady_clock::now(); vector<thread> h; int bloque = N / nhilos; for (int k = 0; k < nhilos; ++k) { int desde = k * bloque; int hasta = (k == nhilos-1) ? N : desde + bloque; // el último, el resto h.emplace_back(sumar_filas, desde, hasta); } for (thread &t : h) t.join(); auto t1 = chrono::steady_clock::now(); return chrono::duration_cast<chrono::microseconds>(t1-t0).count() / 1000.0; }

El detalle que suele fallar: el último bloque tiene que llegar hasta N, porque si N no es múltiplo del número de hilos quedarían filas sin sumar.

Los tiempos típicos en una máquina de 4 núcleos son del orden de 1 hilo ≈ 6 ms, 2 hilos ≈ 3,5 ms, 4 hilos ≈ 2,5 ms: la mejora no es proporcional al número de hilos, porque esta operación está limitada por el acceso a memoria, no por la CPU.

2) El contador compartido.

int contador = 0; // compartido void incrementar(int veces) { for (int i = 0; i < veces; ++i) ++contador; // ¡CONDICIÓN DE CARRERA! } int main() { vector<thread> h; for (int k = 0; k < 4; ++k) h.emplace_back(incrementar, 100000); for (thread &t : h) t.join(); cout << contador << endl; // ¿400000? }

El valor esperado es 400 000, pero sale casi siempre menos, y un número distinto en cada ejecución. El motivo es que ++contador no es una instrucción: son tres.

Hilo AHilo Bcontador
lee 1010
lee 1010
suma → 1110
suma → 1110
escribe 1111
escribe 1111

Dos incrementos y el contador sólo ha subido uno. Cada vez que el planificador intercala así las instrucciones se pierde una cuenta, y por eso el resultado es menor y distinto cada vez.

Las dos soluciones, que se desarrollan en el tema siguiente:

mutex m; void incrementar(int veces) { for (int i=0;i<veces;++i) { lock_guard<mutex> lk(m); ++contador; } } // o bien, sin bloqueo: atomic<int> contador{0}; // ++contador ya es indivisible

Con el mutex sale exactamente 400 000, pero el programa es más lento que con un solo hilo: el coste de bloquear y desbloquear en cada incremento supera con creces lo que se gana. La versión atomic es bastante más rápida. Y la versión realmente buena es que cada hilo acumule en una variable local y sume al total una sola vez al final. Esa es la lección: lo caro no es el paralelismo, es compartir.

Ejercicios resueltos

Intenta cada uno antes de desplegar la solución.

Ejercicio 1 · Resultado de dos hilos

Un hilo suma 1..100 y otro 1..200, cada uno guardando su resultado con ref. ¿Qué vale cada uno? (\(\sum_{i=1}^n i=n(n+1)/2\)).

✓Ver solución paso a paso

\(100\cdot101/2=5050\) y \(200\cdot201/2=20100\). Sin ref() los valores se habrían guardado en copias y las variables originales seguirían a 0.

Ejercicio 2 · Contador sin proteger

Dos hilos hacen cada uno for (i<100000) ++n; sobre un int n compartido, sin mutex. ¿Qué valor esperaríamos y qué valor puede salir?

✓Ver solución paso a paso

Esperado: 200 000. Real: cualquier valor entre 100 000 y 200 000 (cambia de una ejecución a otra), porque los incrementos concurrentes se pisan. Se arregla con lock_guard<mutex> dentro del bucle o con atomic<int>.

Ejercicio 3 · Aceleración (Amdahl)

Un programa tiene un 10 % secuencial. ¿Qué aceleración da con 4 y con 8 núcleos y cuál es el máximo teórico?

✓Ver solución paso a paso

\(S_4=\dfrac{1}{0{,}1+0{,}9/4}=3{,}08\); \(S_8=\dfrac{1}{0{,}1+0{,}9/8}=4{,}71\). Máximo (\(N\to\infty\)): \(1/0{,}1=10\).

Autoevaluación

Responde antes de desplegar.

1¿Qué comparten los hilos de un mismo proceso?

La memoria y los recursos. Cada uno tiene su pila, pero el montón y las variables globales son comunes.

2¿Qué pasa si no se llama a join() ni a detach()?

El destructor de thread llama a terminate() y el programa aborta.

3¿Por qué hay que usar ref() al pasar una referencia a un hilo?

Porque thread copia sus argumentos por defecto; ref() envuelve la referencia para que llegue como tal.

4¿Qué es una condición de carrera?

Que dos o más hilos accedan al mismo dato sin sincronizar y al menos uno escriba: el resultado depende del orden de ejecución.

5¿Por qué ++contador no es seguro entre hilos?

Porque son tres operaciones (leer, sumar, escribir) y otro hilo puede intercalarse entre ellas.

6¿Cómo devuelve resultados la función de un hilo?

Por referencia, porque devuelve void. También puede usarse un atributo del objeto si el hilo ejecuta un método.
